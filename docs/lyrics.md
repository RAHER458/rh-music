# Текст песни (Lyrics Sync)

Синхронизированный с воспроизведением текст в RH—MUSIC: построчная подсветка,
автопрокрутка, ручное чтение и возврат к текущей строке. Архитектура готова к
word-level (слово-в-слово), но первая версия — стабильная построчная синхронизация.

## Проверка источников (факты, не предположения)

Проверка выполнена на реальном API Zvuk с анонимным токеном каталога (тот же
формат, что используется в Worker). Токены в логах, отчётах и репозитории не
публиковались.

| Что проверено | Результат |
|---|---|
| GraphQL-поле `lyrics` у трека | **Boolean-признак**, не текст (`lyrics: true/false`) |
| `GET https://zvuk.com/api/tiny/lyrics?track_id=<id>` | Работает; отдаёт `{ result: { lyrics, type, translation } }` |
| `type: "subtitle"` | LRC с таймкодами `[mm:ss.xx]` — синхронизированный текст |
| `type: "lyrics"` | обычный текст без таймкодов |
| `type: null`, пустой `lyrics` | текста нет (в т.ч. инструментальные композиции) |
| `translation` | поле присутствует, но в проверенной выборке всегда `null` |
| word-level `<mm:ss.xx>` | в Zvuk не встречался |
| антибот | tiny-API отвечает `307` и ставит cookie, затем `200`; Worker переносит cookie между хопами |
| ошибки | `422` на некорректный `track_id`, `404`/пустой результат на отсутствующий текст |

Выборка 20+ треков: русский рок и поп, хип-хоп, зарубежная поп-музыка,
инструментальные композиции (Einaudi, Mozart), треки без текста (Земфира).
Примеры: «Кино — Группа крови» (`subtitle`, 27 строк), «The Weeknd — Blinding
Lights» (`subtitle`), «Miyagi — Marlboro» (`lyrics`, обычный текст), «Einaudi —
Experience» (текста нет, LRCLIB подтверждает инструментал).

## Источники и порядок

1. **Zvuk** — основной. `GET https://zvuk.com/api/tiny/lyrics?track_id=<id>` с
   `X-Auth-Token` из секрета Worker. Текст не покидает сервер без нормализации.
2. **LRCLIB** — если Zvuk не дал синхронизированного текста.
   `GET https://lrclib.net/api/get?track_name=&artist_name=&album_name=&duration=`.
   Если точного совпадения нет — `/api/search?track_name=&artist_name=` с жёсткой
   проверкой: совпадение названия и исполнителя, длительность ±3 % (минимум ±4 с),
   совпадение версии (remix/live/acoustic/cover/remaster и т. п.). Случайный текст
   по похожему названию не принимается. Передаётся осмысленный `User-Agent`.
3. **LiriQo** — не подключён. Причины: замеренная задержка 3,7–3,8 с на запрос,
   отсутствие SLA и ключа, а также риск выдать перевод (английский текст для
   русской песни) за оригинал. Zvuk + LRCLIB покрывают проверенную выборку.

## API

`GET /api/lyrics/:trackId` — единый формат независимо от источника:

```json
{
  "ok": true,
  "trackId": "54018220",
  "source": "zvuk",
  "sourceLabel": "Zvuk",
  "syncLevel": "line",
  "offsetMs": 0,
  "lines": [{ "t": 45430, "text": "Тёплое место, но улицы ждут", "end": 48880 }],
  "plain": null,
  "instrumental": false,
  "attribution": "Текст: Zvuk",
  "fetchedAt": "2026-11-19T08:00:00.000Z",
  "cached": false
}
```

* `syncLevel`: `line` | `plain` | `instrumental` | `none`.
* `lines` заполняется только для `line` (в будущем — `word`), `plain` — только для
  `plain`. Обычный текст никогда не выдаётся за синхронизированный.
* `offsetMs` — сдвиг из LRC `[offset:]`: строка активна при
  `currentTime * 1000 >= t + offsetMs` (клиент ищет по `currentTime - offset`).
* Ошибки сети/429/5xx всех источников — `502 { ok:false, error.code:"LYRICS_UNAVAILABLE" }`;
  такие ответы не кешируются. Неизвестный трек — `404`.

## Кеш

* Cloudflare Cache API (`caches.default`), ключ — `<origin>/__lyrics-cache/v1/<trackId>`.
* Найденный текст (line/plain/instrumental) — 7 суток; отсутствие текста — 1 сутки.
* Ошибки не кешируются. Плюс небольшой in-memory кеш на изолят (до 300 записей).
* Клиенту отдаётся `Cache-Control: public, max-age=300`, чтобы браузер не ходил
  за одним и тем же текстом при каждом открытии панели.

## Движок синхронизации

`web/lyrics.js` работает поверх существующего `<audio id="audio">`:

* события `timeupdate`, `seeked`, `playing`, `loadedmetadata`; пауза не сбрасывает
  строку; смена трека сразу очищает старый текст и загружает новый;
* текущая строка — бинарный поиск последней `t <= currentTime - offset`; никаких
  постоянных `setInterval`/`requestAnimationFrame`;
* устаревшие ответы отменяются `AbortController` и номером запроса — при быстром
  переключении треков текст предыдущего трека не подменяет новый;
* автопрокрутка только при смене строки, `prefers-reduced-motion` учитывается;
* ручная прокрутка (`wheel`/`touchstart`/клавиши) отключает следование, подсветка
  продолжается; кнопка «К текущей строке» возвращает автопрокрутку;
* клик по строке перематывает существующий плеер.

## Интерфейсы

* **Desktop UI** — вкладки «Очередь» / «Текст» в уже существующей правой панели.
  Очередь не удаляется, панель, сайдбар, топбар и плеер не меняются. Кнопка «Текст»
  в правой группе плеера и клавиша `L`.
* **Mobile UI** — полноэкранный слой из экрана текущего трека: чип «Текст»,
  закрытие кнопкой и свайпом по шапке, `100dvh`, safe-area, без горизонтального
  переполнения, без конфликта с таббаром, мини-плеером и шторкой очереди.

Попутно исправлен существовавший конфликт: класс `body.np-open` совпадал с
классом кнопки `.np-open` и делал `body` flex-контейнером, из-за чего при
открытом экране текущего трека страница растягивалась по ширине. Стиль кнопки
ограничен `button.np-open`; горизонтального переполнения больше нет.

Все новые стили и разметка изолированы по средам (`html[data-ui="desktop"]` /
`html[data-ui="mobile"]`, `data-ui-only`), раскладка существующих компонентов
по-прежнему задаётся прежними медиазапросами.
