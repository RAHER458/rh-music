# RH—MUSIC

Полноценный музыкальный веб-сервис: регистрация и вход, личная библиотека, плейлисты,
история прослушивания и **персональные рекомендации, построенные на реальной активности**
пользователя. Поиск и воспроизведение работают по каталогу Zvuk через прокси Cloudflare Worker.

* **Сайт:** https://rh-music.pages.dev
* **API:** https://rh-music.pages.dev/api (тот же домен, что и сайт — см. «Архитектура»)
* **Worker:** https://rh-music-api.rh-launcher.workers.dev
* **Репозиторий:** https://github.com/RAHER458/rh-music

## Архитектура

```
iPhone / браузер
      │  HTML + CSS + JS  (Cloudflare Pages: rh-music.pages.dev)
      │  /api/*  ──►  Pages Function (_worker.js)  ──►  Worker rh-music-api
      ▼
Cloudflare Worker  rh-music-api
      ├── каталог: GraphQL (секрет ZVUK_TOKEN) → подписанный MP3 → Range/206
      └── данные сервиса: Cloudflare D1 (аккаунты, библиотека, плейлисты, история, аффинити)
```

Зачем прокси через Pages: сессионная cookie должна быть **first-party**. iOS Safari блокирует
сторонние cookie, поэтому запросы к API идут с того же домена, что и сайт, а Pages Function
(`web/_worker.js`) перенаправляет их в Worker. Статика остаётся на существующем домене Pages.

Пароли и токены никогда не попадают в браузер: в localStorage лежат только пользовательские
настройки интерфейса (последние поисковые запросы), сессия — в HttpOnly cookie.

## Возможности

**Аккаунты.** Один внутренний аккаунт RH—MUSIC на два способа входа: email с паролем и Google. Регистрация, вход, выход, профиль, смена пароля, привязка и отвязка
провайдеров, полное удаление аккаунта с повторным подтверждением личности. Сессия
восстанавливается автоматически при повторном открытии сайта.

**Витрина (главная).** Общий для всех музыкальный контент каталога: плейлисты по жанрам,
новые альбомы с настоящими датами релизов, исполнители и треки. Не зависит от истории
пользователя, доступна гостям, кэшируется на 15 минут.

**Моя музыка.** Сохранение треков из поиска, списков, страниц альбомов и из плеера.
Повторное добавление не создаёт дубликатов (`PRIMARY KEY (user_id, track_id)`).
Удаление убирает только запись из личной библиотеки. В библиотеке есть поиск, сортировка
и воспроизведение всех сохранённых треков.

**Плейлисты.** Создание, переименование, описание, удаление, добавление и удаление треков,
изменение порядка, воспроизведение и перемешивание. Обложкой служит обложка первого трека —
никаких загрузок файлов и платного хранилища. Удаление трека из библиотеки не удаляет его
из плейлистов.

**История прослушивания.** Записывается при старте трека и подтверждается порциями:
каждые ~25 секунд воспроизведения и при паузе/завершении/уходе со страницы. Хранятся
длительность прослушивания и факт завершения. История видна в разделе «Недавние».

**Рекомендации (отдельная вкладка).** Никаких заранее заданных списков исполнителей и запросов: разделы
строятся только по данным аккаунта — прослушивания (количество, длительность, завершения,
давность), библиотека и плейлисты. Каталог используется как источник похожих исполнителей
(`relatedArtists`) и релизов, данные подтягиваются пакетно (1–2 запроса на всю страницу).
Разделы: «Продолжить прослушивание», «Для вас», «Похоже на …», «Новые релизы»,
«Популярно на RH—MUSIC» (реальная агрегированная статистика сервиса, появляется только
когда данных достаточно). Новому пользователю показывается честное пустое состояние.

**Текст песни (Lyrics Sync).** Синхронизированный с воспроизведением текст: текущая строка
подсвечивается, список плавно следует за ней и останавливается, когда пользователь листает
сам. На десктопе текст живёт вкладкой «Текст» в существующей правой панели (очередь
сохраняется и переключается обратно), на телефоне — отдельным полноэкранным слоем из
экрана текущего трека с закрытием кнопкой и свайпом по шапке. Источники: Zvuk (основной,
LRC из tiny-API), затем LRCLIB (точное совпадение по длительности и версии); обычный текст
показывается без ложной синхронизации, инструментальные треки и отсутствие текста —
честными состояниями. Ответы кэшируются на 7 дней (отсутствие текста — на сутки), ошибки
источников не кешируются. См. [docs/lyrics.md](docs/lyrics.md).

**Плеер.** Поиск, воспроизведение, пауза, переключение треков, перемотка, очередь,
перемешивание, повтор, Media Session (экран блокировки), Now Playing на весь экран.
Мини-плеер скрыт, пока не выбран ни один трек, и не занимает место: панель появляется
только при выбранном треке, остаётся на паузе и восстанавливает последний трек и позицию
после перезагрузки страницы. Плеер можно убрать кнопкой или свайпом вниз — воспроизведение,
очередь и позиция при этом не меняются. Пока панель скрыта, в шапке показывается компактный
плеер: обложка, бегущее название (только если не помещается), исполнитель и рабочая кнопка
Play/Pause; нажатие на обложку или название возвращает нижнюю панель.

Нижние панели закрываются кнопкой, нажатием на фон, Escape и свайпом вниз по ручке;
жест работает только на ручке, поэтому прокрутка содержимого и карусели не конфликтуют.
Качество фиксировано: всегда MID (MP3 128 кбит/с) — переключателя качества в интерфейсе нет.

## Интерфейс

Компоновка desktop-first, ориентир — Koel (левая панель, центральная область, правая панель
очереди, постоянный нижний плеер), визуальный язык — собственный RH—MUSIC.

| Область | Что внутри |
|---|---|
| Левая панель (264–288 px, сворачивается) | логотип, «Обзор» (Главная, Поиск, Рекомендации), «Моя библиотека» (Моя музыка, Любимые треки, Альбомы, Исполнители, Плейлисты, История), список плейлистов, профиль, настройки, выход |
| Верхняя панель | назад/вперёд, заголовок раздела, поиск, компактный плеер, переключатель очереди, аккаунт |
| Правая панель (336–360 px, скрыта по умолчанию) | обложка и метаданные текущего трека, действия, очередь воспроизведения |
| Нижний плеер (≈103 px, постоянный) | слева обложка, название, исполнитель и лайк; в центре перемешивание, пред/play/next, повтор, полоса прогресса и время; справа громкость, очередь, скрытие панели |

Точки перехода: 700 px (планшет), 1024 px (десктоп), 1280/1600/1920 px (ширина панелей и сетки
карточек). Ниже 1024 px сохраняется прежний мобильный интерфейс с таббаром и мини-плеером.

Мобильная версия — основная. Нижняя навигация: **Главная · Поиск · Рекомендации · Моя музыка ·
Плейлисты**. История прослушивания живёт внутри «Моей музыки» (кнопка «История»), чтобы не
перегружать нижнюю панель. На широких экранах (≥1024 px) появляется боковая панель, таббар
скрывается; на страницах входа таббар не показывается.

Главная — витрина: крупный hero-блок с подборкой каталога, горизонтальные карусели
(плейлисты по жанрам, новые альбомы, исполнители) и список треков. Рекомендации — отдельная
вкладка со своими секциями. Мини-плеер и полноэкранный «Сейчас играет» работают поверх всех
страниц.

## Структура D1

| Таблица | Назначение | Ключи и индексы |
|---|---|---|
| `users` | аккаунты: имя, email, хеш и соль пароля, число итераций | уникальные индексы по `username`, `email` (COLLATE NOCASE) |
| `sessions` | сессии: SHA-256 хеш токена, срок, ip/UA | PK `id`, уникальный `token_hash`, индексы `user_id`, `expires_at` |
| `library_tracks` | сохранённые треки | PK `(user_id, track_id)` — дубликатов нет, FK → `users(id)` ON DELETE CASCADE |
| `playlists` | плейлисты | FK → `users(id)`, индекс `(user_id, updated_at)` |
| `playlist_tracks` | треки плейлиста и порядок | PK `(playlist_id, track_id)`, FK → `playlists(id)`, индекс `(playlist_id, position)` |
| `listening_history` | история прослушивания | FK → `users(id)`, индексы `(user_id, started_at)`, `(track_id, started_at)` |
| `user_track_affinity` | агрегат по треку для рекомендаций (плейсы, секунды, завершения) | PK `(user_id, track_id)`, индексы по давности/плейсам/исполнителю |
| `user_preferences` | повтор и перемешивание | PK `user_id` |
| `auth_attempts` | ограничение частоты входа и регистрации | индекс `(ip, action, created_at)` |
| `oauth_identities` | привязки внешних аккаунтов (provider, provider_subject, email провайдера) | UNIQUE `(provider, provider_subject)`, FK → `users(id)` CASCADE |
| `oauth_states` | одноразовые состояния OAuth: nonce, PKCE, срок, признак использования | PK `state`, индексы `expires_at`, `link_user_id` |
| `reauth_events` | свежее подтверждение личности для опасных действий (5 минут) | индекс `(user_id, created_at)` |
| `home_snapshot` | снимок витрины главной, общий для всех посетителей | PK `key` |
| `session_methods` | каким способом создана конкретная сессия (для плашки «текущий вход») | PK `token_hash`, FK → `users(id)` CASCADE |

Миграции: `worker/migrations/*.sql`, применяются `node scripts/db-migrate.mjs`.

## Безопасность

* Пароли — **PBKDF2-SHA256**, 100 000 итераций, индивидуальная соль; сравнение хешей выполняется за постоянное время.
* Сессия — 32 случайных байта; в базе хранится только SHA-256 хеш токена.
* Cookie `HttpOnly; Secure; SameSite=Lax` — токен недоступен из JavaScript.
* CSRF — проверка `Origin` + обязательный заголовок `X-RH-Request` на всех изменяющих запросах.
* Ограничение частоты: регистрация ≤ 6 / 30 мин, вход ≤ 12 / 15 мин на IP.
* Единый ответ «Неверный логин или пароль» и выравнивание времени ответа (защита от перебора аккаунтов).
* Все данные фильтруются по `user_id`; обращение к чужому плейлисту или треку возвращает 404.
* Внешний вход (Google): ID Token проверяется на сервере по JWKS (подпись, `iss`, `aud`, `exp`, `iat`, `nonce`),
  обязателен `email_verified`. Данные, пришедшие из frontend, не считаются доказательством личности.
* `state` и `nonce` одноразовые (таблица `oauth_states`, TTL 10 минут): повторная отправка того же
  `state`/credential отклоняется, двойная отправка из интерфейса дополнительно блокируется на клиенте.
* Привязка чужого Google-аккаунта невозможна (`UNIQUE (provider, provider_subject)` + проверка `IDENTITY_TAKEN`).
* Аккаунты **не объединяются по совпадению email**: вход через провайдера находит только привязанный
  аккаунт, остальное — явная привязка из настроек после подтверждения личности.
* Отвязка провайдера и удаление аккаунта требуют свежего подтверждения личности (5 минут, одноразово,
  привязано к `user_id`). Последний способ входа отвязать нельзя: проверка и удаление выполняются одним
  атомарным запросом D1, поэтому два параллельных запроса не оставят аккаунт без входа.
* Удаление аккаунта удаляет все привязки, сессии, библиотеку, плейлисты, историю и профиль рекомендаций —
  повторный вход тем же провайдером создаёт новый чистый аккаунт.
* Значение `ZVUK_TOKEN` не читается и не выводится ни в одном ответе.

## Внешняя авторизация

В RH—MUSIC два способа входа: **email + пароль** и **Google** (Google Identity Services).
VK ID и Apple ID не используются и удалены из интерфейса и кода.

Как работает Google:

1. на клиенте официальная кнопка GIS (`renderButton`) получает Google ID Token;
2. frontend отправляет `credential` и одноразовый `state` на `POST /api/auth/oauth/google`;
3. сервер проверяет подпись по официальным JWKS Google, `iss`, `aud` (точное совпадение с
   Client ID), `exp`/`iat`, `nonce` и `email_verified`;
4. по паре `(provider, provider_subject)` находится существующий аккаунт RH—MUSIC или создаётся
   новый; выдаётся обычная сессия RH—MUSIC в HttpOnly cookie.

Client secret не нужен и не хранится. Redirect-flow не используется.

| Переменная | Тип | Значение |
|---|---|---|
| `GOOGLE_CLIENT_ID` | public (`plain_text`) | `350559220212-e8jd27djhpdt3fqq1e7tjepm8dnjsq2s.apps.googleusercontent.com` |
| `SITE_URL` | public, необязательно | `https://rh-music.pages.dev` |

Authorized JavaScript origin в Google Cloud Console: `https://rh-music.pages.dev`.
Redirect URI для этой схемы не требуется — не добавляйте выдуманные адреса.

Проверить состояние можно так: `GET /api/auth/providers` → `{"providers":[{"id":"google","enabled":true,...}]}`.
Если `GOOGLE_CLIENT_ID` не задан, сервер отвечает `503 PROVIDER_DISABLED`, а в интерфейсе вместо кнопки
показывается понятное сообщение — «имитации» входа нет.

Обновление Worker с Client ID:

```bash
GOOGLE_CLIENT_ID=350559220212-e8jd27djhpdt3fqq1e7tjepm8dnjsq2s.apps.googleusercontent.com \
  node scripts/deploy-worker.mjs
```

## Деплой

```bash
export CLOUDFLARE_API_TOKEN=...        # Workers Scripts:Edit, Pages:Edit, D1:Edit
export CLOUDFLARE_ACCOUNT_ID=...
export D1_DATABASE_ID=...              # id базы rh-music-db
export ZVUK_TOKEN=...                  # только при первой установке секрета

node scripts/db-migrate.mjs            # миграции D1
node scripts/deploy-worker.mjs         # Worker + D1-биндинг (секрет сохраняется)
node scripts/deploy-pages.mjs          # статика + Pages Function (прокси /api)
node tests/oauth.mjs                   # 83 проверки внешней авторизации на локальном SQLite
node tests/player.mjs                  # 39 проверок видимости и скрытия мини-плеера
node tests/ui.mjs                      # 45 проверок навигации, панелей и жестов
```

`scripts/deploy-worker.mjs` передаёт `keep_bindings: ["secret_text"]`, поэтому обновление
кода не стирает `ZVUK_TOKEN`. Автодеплой — `.github/workflows/deploy.yml`
(workflow_dispatch или пуш в `main`).

## Ограничения

* Проект неофициальный и не связан с Zvuk.com; для работы нужен собственный токен каталога.
* Раздела «Популярное» может не быть, пока в сервисе мало прослушиваний — это честное поведение,
  а не отсутствие функции.
* Аудиофайлы нигде не сохраняются: плеер получает подписанный поток по Range и не кэширует его.
* Публичный GraphQL каталога не предоставляет метода «редакционная выдача главной» (доступны только
  `search`, `getTracks`, `getArtists`, `getReleases`, `playlists(ids)`, `genres(ids)`), поэтому витрина
  собирается из реальных объектов каталога по жанровым запросам. Обложки плейлистов строятся из обложек
  их треков: серверы каталога не отдают статические обложки плейлистов.
* Внешний вход — только Google; без `GOOGLE_CLIENT_ID` кнопка не рисуется, а интерфейс честно
  сообщает, что способ пока недоступен.
* Для Google-аккаунтов нет отдельной формы «задать пароль»: добавить email-вход к такому аккаунту пока
  нельзя, поэтому отвязать единственный способ входа такая учётная запись не может — это осознанное
  ограничение, а не ошибка.
